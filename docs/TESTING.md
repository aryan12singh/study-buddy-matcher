# Testing

How the project is tested, how to run the suites, what each area's tests cover, and the
acceptance scenarios used for demos. Endpoint and DTO details are in
[API_CONTRACT.md](API_CONTRACT.md); configuration keys are in the
[README](../README.md#configuration); migrations and the demo reset are in
[DATABASE.md](DATABASE.md).

## 1. Strategy

Each kind of rule is tested at the boundary where it can actually break.

| Layer | What it is for | Where |
| --- | --- | --- |
| Unit tests | Pure rules with no I/O: scorers, `TimeSlot` interval maths, value objects (`MatchScore`, `MatchingWeights`), strategies and priority tiers, state machines (`MatchRequest`, `Connection`, `StudyGroup`, `GroupJoinRequest`), the Pomodoro timer, session schedules and calendar output, badge/streak rules, AI prompt builders and output validators | `backend/src/test/java/com/studybuddy/<feature>/` |
| HTTP integration tests | The real Spring web, security, JWT and JPA stack against a real PostgreSQL database. Used for ownership and role checks, contact privacy, concurrency (last group place, simultaneous accept/decline, racing admin saves), transactional rollback and query counts | `backend/src/test/java/com/studybuddy/integration/`, all extending `PostgresHttpTest` |
| Context-load test | Fails if a bean cannot be wired, a configuration property is missing or an entity mapping does not match the migrated schema (`ddl-auto: validate`) | `StudyBuddyApplicationTests` |
| Migration tests | Fresh, legacy-upgrade, failed-preflight rollback and populated repeat migrations; demo-reset preservation | `scripts/test-migrations.sh` with fixtures in `scripts/sql/` |
| Frontend interaction tests | Rendered components with Vitest and Testing Library: empty/loading/error states, form validation, dirty-draft guards, stale responses after navigation, confirmation dialogs | `frontend/src/**/*.test.tsx` and `*.test.ts` |

External providers (Gemini, Open-Meteo weather, Spotify, Freesound) are never called by the
default suites. HTTP tests replace the AI client with a fake, the test profile disables
weather, and provider clients are unit-tested against recorded or synthetic replies. Two
opt-in tests, `GeminiClientLiveTest` and `StudyPlanPromptLiveTest`, run only when
`GEMINI_LIVE_TEST_KEY` is set; CI does not set it.

## 2. How to run

### Prerequisites

Java 21, Node 22 with npm, Docker, the PostgreSQL client (`psql`) and OpenSSL.

### Full backend suite

From the repository root:

```bash
scripts/test-backend.sh
```

The script:

1. starts a private, disposable `postgres:17` container on a random local port, with a
   password and JWT signing key generated by OpenSSL for this run only;
2. waits until the published TCP port accepts SQL (not just the container's internal socket);
3. creates `studybuddy_migration_test` and runs `scripts/test-migrations.sh` against it;
4. applies the ordered migrations to `studybuddy_test` with `scripts/migrate-database.sh`;
5. exports the test-profile variables and runs `./mvnw -B test` in `backend/`;
6. removes the container and its credentials file on exit.

Arguments are passed to Maven, so a focused run still gets a fresh database:

```bash
scripts/test-backend.sh -Dtest='com.studybuddy.matching.**' -Dsurefire.failIfNoSpecifiedTests=false
scripts/test-backend.sh '-Dtest=MatchServiceTest,Explanation*Test,MatchExplanationServiceTest,MatchExplanationHttpTest,GeminiExplanationProviderTest'
```

The suites never touch the shared database. `PostgresHttpTest` refuses to run unless the
connected database is `studybuddy_test`, and `test-migrations.sh` refuses anything except an
empty `studybuddy_migration_test`.

### Unit tests only (no database)

```bash
cd backend
./mvnw test -Dtest='!com.studybuddy.integration.**,!StudyBuddyApplicationTests' \
  -Dsurefire.failIfNoSpecifiedTests=false
```

### Against your own disposable database

To run the suite without Docker, point it at a PostgreSQL 17 server you can wipe. These are
the variables CI sets (`.github/workflows/ci.yml`); substitute your own host, port and password:

```bash
# Read by scripts/test-migrations.sh and scripts/migrate-database.sh
export PGHOST=localhost PGPORT=5432 PGDATABASE=studybuddy_test PGUSER=studybuddy_test
export PGPASSWORD='<disposable password>'

# Read by the backend's test profile (backend/src/test/resources/application-test.yml)
export SPRING_PROFILES_ACTIVE=test
export STUDYBUDDY_TEST_DATABASE_URL=jdbc:postgresql://localhost:5432/studybuddy_test
export STUDYBUDDY_TEST_DATABASE_USERNAME=studybuddy_test
export STUDYBUDDY_TEST_DATABASE_PASSWORD="$PGPASSWORD"
export STUDYBUDDY_TEST_JWT_SECRET="$(openssl rand -base64 48)"

psql --no-psqlrc --set=ON_ERROR_STOP=1 --command='CREATE DATABASE studybuddy_migration_test'
PGDATABASE=studybuddy_migration_test scripts/test-migrations.sh
scripts/migrate-database.sh
cd backend && ./mvnw -B test
```

The test profile never loads `application-local.yml`. It disables weather requests and the
demo seeder, and raises the login-throttle limit so unrelated tests cannot lock an account
(`LoginThrottleHttpTest` sets its own low limit).

### Frontend

From `frontend/`:

```bash
npm ci
npm test            # vitest run
npm test -- src/features/matching src/features/home   # focused folders
npm run lint        # oxlint
npm run build       # tsc -b && vite build
```

On a heavily loaded machine, `npm test -- --maxWorkers=1` avoids asynchronous test timeouts.

## 3. What CI runs

`.github/workflows/ci.yml` runs two jobs on every pull request into `main`, on every push to
`main` and on manual dispatch.

| Job | Steps |
| --- | --- |
| Backend tests and PostgreSQL integrity | `postgres:17` service; JDK 21 (Temurin); generate a masked JWT test key with OpenSSL; create `studybuddy_migration_test` and run `scripts/test-migrations.sh`; run `scripts/migrate-database.sh` twice against `studybuddy_test` to prove it repeats safely; `./mvnw -B clean test` |
| Frontend interactions, lint and build | Node 22; `npm ci`; `npm test`; `npm run lint`; `npm run build` |

## 5. Scoring fixtures worth explaining

Scores describe preference compatibility, not whether students will succeed together. The
Balanced default weights in `application.yml` (`app.matching.default-weights.balanced`) are
course 0.30, availability 0.30, study mode 0.20, study goal 0.10 and group size 0.10. With a
course and goal selected in the current search:

| Criterion | Fixture | Score | Weight | Contribution |
| --- | --- | ---: | ---: | ---: |
| Course | Candidate targets the selected course | 1 | 0.30 | 0.30 |
| Availability | Each student has 6 unique free hours, of which 3 are shared | 0.5 | 0.30 | 0.15 |
| Study mode | Caller online; candidate either | 1 | 0.20 | 0.20 |
| Goal | Candidate has the selected goal | 1 | 0.10 | 0.10 |
| Group size | Candidate has not supplied a range (unknown) | 0 | 0.10 | 0 |
| Total | Sum of contributions | | 1.00 | **0.75** |

With the default quality cut-offs (`quality.strong: 0.75`, `quality.good: 0.50`) this is a
Strong match, shown as 75% compatibility. The exact total drives ranking, threshold and
quality. The missing group range scores `scoring.unknown-score` (0), the card shows
"Not shared", and a group-size filter cannot treat it as compatible.

Availability divides shared time by the smaller of the two timetables
(`AvailabilityOverlapScorer`), so the score is the same from either side and listing a lot of
free time is not penalised. Shared blocks shorter than `scoring.min-session-minutes` (60) do
not count.

**Appendix A.** `AppendixAMatchingTest` reproduces the brief's worked example with the real
scorers and Balanced weights. Student A (IS442; Wed 19:00–21:00 and Fri 14:00–16:00; in
person; exam preparation; 2–3 students) against Student B (IS442; Wed 19:00–21:00 and Thu
18:00–20:00; either mode; exam preparation; 2 students):

- course 1, study mode 1 (in person vs either), goal 1, group size 1 (2–3 overlaps 2);
- each timetable totals 4 hours and the one shared block is 2 hours, so availability is
  2/4 = 0.5;
- total 0.30 + 0.15 + 0.20 + 0.10 + 0.10 = **0.85**, Strong, and identical from B's side.

Adding a duplicate or nested shared block keeps shared time at 2 hours; two blocks that only
meet at 21:00 share nothing. Weekly slots are Singapore wall-clock times.

**Strategies.** Fixtures put a higher priority band against a larger weighted total.
Availability-first ranks by shared-hour bands (`priority-tiers.availability-hours`: 3 h or
more, 1 to 3 h, under 1 h) before the total. Course-first uses bands at 1 and
`takes-course-score` (wants a buddy for the course, takes it, neither). An unknown priority
criterion falls in the lowest band; within a band the total decides. Disabling the priority
criterion removes that comparison. Ties break on more shared hours, then case-insensitive
name, then ID. The Most shared hours and Same year first sorts add their comparison before
this chain.

## 6. Demo walkthroughs

Use synthetic seeded accounts on a local or disposable database. The seeder needs its
passwords from `application-local.yml`; none are recorded here. The seeded presenter already
has sessions, quizzes, a study plan and badges, so only the steps that create something new
need Gemini.

### Matching

1. Sign in as a student with no saved target or goal. Home explains the next step and links to
   preferences without calling `GET /api/matches`.
2. Open Find buddies and search by course only, then by goal only. A course different from the
   saved target is the one scored.
3. Check names, programme/year, total, quality and criterion bars against the API payload, and
   the shared-hours total against the heatmap.
4. With a saved target or goal, Home shows up to three results from the same ranking; its link
   keeps the search context.
5. Add and remove mode, group size, goal, minimum shared hours and minimum quality filters;
   reset returns to the first-use state.
6. Try Best match, Most shared hours and Same year first. The screen order matches the API;
   quality badges never regroup cards.
7. Use incompatible filters to get no results: an explanatory empty state with a reset action,
   not an error.

### Requests and privacy

1. Search results exclude the caller, inactive accounts and active buddies; pending requests
   show the right disabled or response action.
2. Open a stranger's profile and inspect the network response: no contact, email or token.
3. Send a match request with an optional message. The card shows pending as soon as the POST
   succeeds; a failed POST allows retry. "View your requests" opens Outgoing.
4. As the receiver, follow the notification, accept, and confirm contact appears only in the
   connected profile. The connection leaves search results.
5. End the connection: contact disappears from the profile again. Separately, cancel a pending
   request as sender; the recipient sees it in Past requests and can no longer accept it.

### Groups

1. Create a course group with goals, mode, capacity and a weekly schedule; edit it. An invalid
   time (`25:00`) blocks the save and leaving asks to discard.
2. Apply as another student, approve as leader and check the member count. Ordinary members
   cannot manage and do not see contact.
3. Withdraw a pending application, then apply again.
4. As a member, leave the group (confirmation first): room and session access end, other
   members are unaffected. The leader cannot leave and must close the group instead.
5. Remove a member, then close the group; it becomes inactive.

### Admin matching configuration

1. As admin, open Matching settings and note the revision. Each strategy keeps its own five
   weights.
2. Disable the active priority criterion, rebalance and save; a student search falls back to
   total-only ranking. Re-enable it and show the priority with the opposing-total fixture.
3. Save fractional weights such as 0.004/0.996; reload and confirm they are exact. A threshold
   filters lower totals.
4. Negative weights, a zero total, an invalid sum, no enabled criteria or an invalid threshold
   are rejected and the last valid settings are kept.
5. Save from one admin session, then save from a second session on the old revision: it gets a
   conflict and offers reload. Unsaved edits are kept.
6. Restart the backend: overrides and revision persist. Restore defaults confirms first, clears
   overrides and raises the revision.
7. Student and anonymous reads or writes of the configuration are rejected.

### Admin accounts

1. Create and edit a synthetic student. Admin responses never contain the contact number;
   omitting contact on edit keeps the existing value.
2. View usage: last sign-in, active connections and open groups.
3. Deactivate a connected student: the old token stops working and sign-in returns 403.
   Reactivate: a fresh sign-in works and former relationships stay ended.
4. Permanently delete a separate synthetic account after typed confirmation; its token is
   rejected. Self-removal controls are unavailable.

### Study rooms and sessions

1. In two browsers, join the same group room. The leader assigns host and co-host; delegated
   roles cannot reassign roles. Start, pause, resume and reset the timer. Countdowns follow
   server state through polling, not exact tick synchronisation.
2. Refresh, reconnect and close one of several tabs: timer state is durable, a student counts
   once against capacity, and expired presence must rejoin explicitly. Remove a member, fill
   the place, readmit them: the old heartbeat fails and a fresh join respects the limit.
3. Open the Music tab in a personal and a group room. Play the free Spotify playlist and layer
   two ambient sounds; change volumes, remix, stop all. Only your browser hears it, and
   leaving the page stops every sound.
4. Create, edit and cancel a dated weekly group session with time zone, agenda and location.
   Home and the agenda show the saved sessions and recipients are notified. Repeat for a
   connected buddy pair. Strangers and admins are denied.
5. Check mutual availability suggestions; clearing one participant's week empties them while
   manual scheduling still works.
6. Download single and weekly calendar files, including a DST-crossing series, and compare UTC
   times with the API. Exports are refused to strangers, removed members and ended
   connections, and contain no private contact or token.
7. Switch weather themes and day/night; with the provider unavailable the manual themes still
   work, and reduced motion stops scene animation.

### E1 AI match explanations

The free tier allows 20 generate requests per day per project and model, so warm the cache
before a demo.

1. On the demo database, search and click **Explain this match** on every card you will show,
   at least 15 seconds apart. Each shows the **AI** badge.
2. Afterwards do not change the prompt version, model, matching weights or the demo students'
   preferences; any of these needs a fresh call.
3. Warmed cards answer from the cache. If a fresh call is refused, the student sees the
   standard explanation with **Try AI again**, never an error.
4. Change a scoring input after loading a card: the old card is rejected with 409 and the page
   refreshes it before explaining.

### Help

1. With courses, study mode and availability missing, Help shows one setup action and
   separate per-step labels.
2. Send or accept a request: only the relationship check changes; searches are untracked. A
   pending incoming request takes priority.
3. A pending applicant gets no room shortcut. After acceptance, the room link opens a preview;
   joining still needs **Join study room**.
4. Remove membership, close the group or disconnect: private shortcuts disappear. A failed
   source shows "Could not check" with retry, never "incomplete".
5. Every contextual Help link lands on its topic heading, and topics and FAQ work by keyboard.

### Achievements

1. As a new student every badge is locked and the grove is a seed, with usable actions.
2. Join a group or accept a buddy and schedule a recurring session. Planned occurrences count;
   streaks count distinct Monday-based weeks up to the current week.
3. Remove a membership, cancel a session or disconnect: live counts and runs recompute, while each
   earned tier, the points and the level stay; a fallen badge says what its current count alone
   reaches. Founder still counts closed groups and First Move still counts retained requests.
4. A readmitted member's earlier occurrences do not count.
5. Another student's profile shows no achievement summary and makes no achievement request.

### Quizzes, study plans and the assistant

1. In a group room, the host opens Quiz Buddy with notes or a file, a course and a focus.
   Members take the quiz; answers stay hidden until the host closes it or its open window
   ends. The leaderboard ranks by score and highlights the signed-in member.
2. A personal quiz shows answers as soon as it is submitted. An unreadable file is refused
   before anything is sent.
3. Ask Pixel to find a buddy for a course: it shows real match cards without contact details.
   Ask when your group is free, what is waiting for you, or to be quizzed (opens Quiz Buddy).
4. Ask Pixel to plan your study for a course and exam date: the Study plans form opens with
   them filled in. Create the plan, tick off a topic, reload and check it stays ticked, then
   delete the plan after confirming.
5. The suggested questions are answered without an AI call. With Gemini unavailable, Pixel and
   Quiz Buddy say so plainly, and no quiz or study plan is saved.

## 7. Known limits

- Physical-device checks (phone browsers for music playback and interruption, background
  recovery, virtual keyboard, text zoom, clipboard, calendar import), projector readability,
  screen-reader use and comparison with the latest Figma are manual, not automated.
- Calendar files are snapshots: there is no two-way sync, a client may duplicate or ignore
  edited and cancelled events, and an offline copy cannot be revoked. Outlook import has not
  been checked.
- External providers are faked or stubbed in the suites; live behaviour is checked only by the
  opt-in Gemini tests and manual demos.
- AI call quotas and the rate-limit cooldown are held in memory in one process and reset on
  restart; Google's own daily limit resets on Pacific time.
- AI output checks cover format, length, success and likelihood wording, code names, course
  codes and hour figures, not every sentence; the panel says AI text may be inaccurate and the
  score bars stay visible. Simultaneous identical cache misses may each call the provider.
- Room timers stay in step through polling, so clients can differ by the poll period and
  network delay.
- Availability slots are same-day; overnight ranges are not split automatically.
